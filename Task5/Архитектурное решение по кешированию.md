# Архитектурное решение по кешированию

## 1. Цели и мотивация
Кеширование внедряется для достижения следующих целей:
- Уменьшение времени отклика системы.
- Снижение нагрузки на базу данных.
- Ускорение работы пользовательских интерфейсов.
- Повышение стабильности системы при росте нагрузки.

Основные проблемы, которые решает кеширование:
- Медленная работа MES из-за перегруженной базы данных.
- Высокая нагрузка на интернет-магазин при увеличении числа пользователей.

## 2. Критичные компоненты для кеширования
Кеширование будет применяться к следующим компонентам:
- **MES API**: данные дашборда операторов и списки актуальных заказов.
- **Shop API**: информация о товарах и ценах.
- **CRM API**: статусы заказов и клиентские данные.

## 3. Предлагаемое решение
### Клиентское кеширование
**Область применения**: интернет-магазин.  
**Преимущества**:
- Уменьшение количества запросов к серверу.
- Ускорение загрузки страниц.
- Снижение нагрузки на API.

**Реализация**:  
Использование браузерного кеширования с HTTP-заголовками `Cache-Control` и `ETag` для управления инвалидацией.

### Серверное кеширование
**Область применения**: MES API и CRM API.  
**Выбранный паттерн**: Cache-Aside.  
**Преимущества**:
- Данные загружаются в кеш только при первом запросе.
- Исключается кеширование редко используемых данных.
- Автоматическая инвалидация при обновлении данных в базе.
- Дополнительное кеширование архивных данных (например, заказов с финальными статусами).

**Отклонённые паттерны**:
- **Write-Through**: создаёт избыточную нагрузку на кеш-хранилище из-за частых обновлений.
- **Refresh-Ahead**: требует предсказуемых паттернов запросов, что сложно реализовать в MES.

## 4. Инвалидация кеша
### Выбранная стратегия
**Механизм**: pub/sub (издатель-подписчик) с уведомлениями через Redis.  
**Условия инвалидации**:
- Изменение статуса заказа.
- Обновление клиентских данных.

**Преимущества**:
- Мгновенное обновление или удаление данных из кеша.
- Разделение кеша по статусам заказов для снижения избыточной инвалидации.
- Отсутствие лишних запросов к базе данных.

### 4. Инвалидация кеша
### Сравнение стратегий инвалидации

**1. Программная инвалидация (pub/sub)**
- **Точность обновления**: Обновляет только изменённые данные в реальном времени
- **Нагрузка на БД**: Минимальная, так как обновления точечные
- **Сложность реализации**: Требует настройки системы событий (например, через Redis)
- **Преимущества**: Мгновенная синхронизация, нет избыточных запросов
- **Недостатки**: Сложнее в реализации по сравнению с TTL

**2. Временная инвалидация (TTL)**
- **Точность обновления**: Может сохранять устаревшие данные до истечения TTL
- **Нагрузка на БД**: Автоматическое удаление, но возможны пиковые нагрузки при массовом обновлении
- **Сложность реализации**: Очень простая в настройке
- **Преимущества**: Не требует дополнительной инфраструктуры
- **Недостатки**: Нет гарантии актуальности данных между обновлениями

**3. Инвалидация по ключу/Полное обновление**
- **Точность обновления**: Сложная логика для связанных записей
- **Нагрузка на БД**: Высокая, особенно при полном обновлении кеша
- **Сложность реализации**: Сложная, требует тщательного проектирования
- **Преимущества**: Полный контроль над процессом инвалидации
- **Недостатки**: Может удалять ещё актуальные данные, создаёт избыточную нагрузку


## 5. Заключение
Предложенное архитектурное решение обеспечивает баланс между производительностью и актуальностью данных. Клиентское кеширование оптимизирует работу интернет-магазина, а серверное кеширование с паттерном Cache-Aside и механизмом pub/sub для инвалидации эффективно решает задачи MES и CRM API. Это позволяет системе оставаться стабильной даже при высокой нагрузке.
